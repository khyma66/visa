# Temporary picomatch security backports

The public npm releases `picomatch@2.3.2` and `picomatch@4.0.7` are affected by [GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf). On November 18, 2026, the advisory lists no published fixed version. The build uses both major versions, so this release temporarily carries two private forks. Their original MIT licenses, author attribution and READMEs are retained.

The source under `vendor/picomatch-v2` and `vendor/picomatch-v4` starts from the exact npm distributions whose SHA-512 hashes appear in the pre-change lockfile. The only runtime-code changes are the unmerged upstream proposals [#263](https://github.com/micromatch/picomatch/pull/263), commit `9ca61909ab0ec680953e21bac80a6e825e1ede81`, and [#262](https://github.com/micromatch/picomatch/pull/262), commit `3222059ac27492d9c0147fee5c65f751bbd851ab`, respectively. Upstream has not accepted or published these changes. The v4 proposal has an independently published compatibility and bounded-attack review; its tests are finite and do not prove all glob and regex patterns safe. Both patches retain the upstream option `maxExtglobRecursion: false`, which explicitly disables that protection. Do not pass user-supplied glob patterns or disable the guard.

`npm pack` creates the two committed archives in `vendor/`; consumer-specific npm overrides select v2 for `anymatch`, `micromatch`, and `readdirp`, and the v4 dependency supplies Vite and its consumers. npm's relative local-tarball override bookkeeping may cause `npm ls picomatch` to label the nested v2 entries invalid even though `npm ci` installs and resolves them. `scripts/test-picomatch-security.mjs` checks the actual consumer resolutions, every installed source file against the reviewable source, archive integrity, common matching behavior, and bounded exploit cases. A clean install, full application test/build and these security tests are required before release.

`npm audit` cannot inspect the code in private forks or connect new upstream advisories to their new names. It is therefore **not proof that the forks are secure**. In addition to the unchanged high-severity npm audit gate, CI and the guarded production release query the upstream advisory service for the original two versions. That check permits only the reviewed advisory above, rejects changes to its ID, URL, title, severity or affected-version range, and fails closed on any other high or critical finding or a registry failure. It cannot detect changes limited to other advisory fields, identify unreported vulnerabilities or prove a patch complete. Test coverage and source review remain necessary.

When a compatible, maintainer-reviewed release is available for both major versions, remove the forks, archives, package overrides, special advisory check and temporary documentation; update the lockfile and rerun all checks. If only one version is fixed, migrate that version separately and continue monitoring the other.
